## Fase 0 — Cerrar la cola del incidente del alta 🟠

El alta **funciona en producción**. Esta fase no la arregla: recoge lo que quedó suelto cuando se
arregló, para que el pase no lo arrastre.

Contexto, porque explica por qué queda algo suelto: desplegar el alta en servidor (PR #44) destapó
que **las credenciales del Admin SDK en Vercel estaban rotas y nadie lo sabía**. Lo único que las
usaba era `verifyToken`, y `verifyIdToken` **no necesita credenciales válidas** —verifica la firma
contra los certificados públicos de Google—, así que la avería era invisible hasta la primera
operación de administrador real, que fue `createUser`. La causa fue la clave privada pegada con
saltos de línea reales en un campo que los trunca: va en **una sola línea con `\n` literales**.

| # | Cabo suelto | Estado |
|---|---|---|
| 0.1 | **`hotfix/alta-log-admin-sdk` (5d80f6fe) sigue sin mergear.** Está pusheado y va 1 commit por delante de `main`. Es el que hace que los dos caminos de error del alta escriban código y mensaje en el log del servidor | Pendiente. Sin él, el próximo fallo del alta vuelve a diagnosticarse deduciendo de la lista de APIs externas de Vercel |
| 0.2 | La línea `privateapikey.txt` del `.gitignore` está **modificada sin commitear** en el árbol de trabajo | Pendiente. Es lo que impide que la clave acabe en git |
| 0.3 | Desmarcar ***Enable create (sign-up)*** en Identity Platform | Pendiente, y es lo único que cierra `accounts:signUp` de verdad. Turnstile cierra la ficha de Firestore, no la cuenta de Auth: hasta que se desmarque, los bots siguen creando cuentas huérfanas |

**Decisión:** 0.1 y 0.2 son parte del pase y van aquí. **0.3 no bloquea** —es una palanca de consola,
independiente del despliegue del front—, pero conviene hacerla en la misma ventana: es la que corta
el goteo de altas automatizadas, y medir su efecto se hace por fichas nuevas en `users`, no por el
contador de Firebase Auth, que seguirá subiendo hasta entonces.

```bash
git checkout main && git pull origin main
git merge origin/hotfix/alta-log-admin-sdk --no-ff
git push origin main
```

**Puerta de salida:** `main` con el logging dentro, y el `.gitignore` commiteado.

## Fase 1 — Reconciliar `main` → `develop` → `staging` 🟠

`staging` no conoce Turnstile ni el alta en servidor. **Un merge `staging → main` sin reconciliar
antes se lleva por delante los tres hotfixes que hoy protegen producción.**

Se hace en `develop` —que es donde manda la convención— y de ahí sube a `staging`. Como `staging` es
`develop` más merges vacíos, los conflictos se resuelven **una sola vez**.

```bash
git checkout develop && git pull origin develop
git merge origin/main            # 4 conflictos, listados abajo
# …resolver…
npm run lint && npm run build
git push origin develop

git checkout staging && git pull origin staging
git merge develop
git push origin staging
```

### Los 4 conflictos, y cómo se resuelven

Medidos con `git merge-tree --write-tree`, no estimados.

| Fichero | Qué choca | Resolución |
|---|---|---|
| `locales/fr/common.json` | Ambos lados añaden claves | **Quedarse con las dos tandas.** Los otros cuatro diccionarios automergean solos; si el francés choca es por proximidad de líneas, no por contradicción |
| `src/lib/http/serverBackendProxy.ts` | `main` añade `turnstileAction` al tipo y lo activa en `recovery_pass` y `create_user`; `staging` añade `subPathPattern` y 4 handlers nuevos | **Los dos campos y los dos conjuntos de handlers.** Es mecánico: no se contradicen, solo tocan el mismo bloque |
| `src/app/main/user/account/page.controller.tsx` | `main` mete el widget de Turnstile en el cambio de contraseña; `staging` quita la subida de foto y pone avatar con la inicial | **Los dos.** Cuidado con los imports: `staging` retira `Image`, `main` añade `TurnstileWidget` |
| `src/app/auth/register/page.controller.tsx` | `main` sustituye el alta entera por la llamada al servidor; `staging` añade recuperación de un alta a medias | **Gana `main`, entero** — razonado abajo |

### Por qué en el registro gana `main` sin discusión

`staging` añadió un apaño real: si `createUser` daba `auth/email-already-in-use`, entraba con la
contraseña y remataba la ficha que quedó a medias. Resolvía un problema que existía porque el alta
eran dos pasos y el segundo podía fallar dejando una cuenta inservible.

**Ese problema ya no existe.** La ruta de servidor tiene `rollback()`: si algo falla después de
crear la cuenta, la borra. No hay estado a medias que recuperar, y `auth/email-already-exists` pasa a
ser una respuesta correcta —409— en vez de un callejón sin salida.

Además, quedarse con el lado de `staging` **rompe el build**: importa `createUser` de
`@/lib/firebase/authentication/create`, y `main` borró ese fichero.

### Comprobación que el merge NO hace sola

`main` protege `recovery_pass` y `create_user` con Turnstile **en el proxy**, así que *todo* el que
los llame tiene que mandar el token. Son cuatro sitios, y el merge automergea dos de ellos sin
garantizar que sigan siendo correctos:

- `/auth/register` · `/auth/recovery` — conflicto, se revisan a mano
- `/main/user/account` — conflicto, se revisa a mano
- **`/main/user/complete-profile`** — automergeado, **hay que mirarlo**: llama a `create_user`

**Puerta de salida:** `npm run build` limpio, y las cuatro pantallas probadas en local o en dev
contra un entorno con Turnstile configurado.

## Fase 4 — El pase 🟢

Con las tres anteriores cerradas, esto es lo aburrido.

```bash
git checkout main && git pull origin main
git merge staging --no-ff -m "merge: staging -> main (pase a producción 05-09-2026)"
# Sin conflictos: staging ya trae main dentro desde la Fase 1
npm ci && npm run lint && npm run build
git push origin main          # dispara el deploy de Vercel
```

Si aquí aparece un conflicto, la Fase 1 no está terminada. **Parar y volver**, no resolverlo aquí:
resolver el mismo conflicto dos veces en dos ramas es como se pierde un hotfix.

| # | Qué | Bien es |

## Fase 6 — Rollback

**Promover el deployment anterior desde el panel de Vercel.** Es lo primero, sin tocar git; deshacer
el merge viene después y con calma.

Las variables nuevas se pueden dejar puestas: el build anterior no las lee.

Ningún cambio de este pase migra datos ni escribe esquema desde el front, así que no hay nada que
revertir en Firestore.

**Ojo con una tentación:** si tras el pase falla el alta, revertir el deploy **no la arregla** —el
alta en servidor está en producción desde el PR #44, por debajo de este pase—. El rollback de verdad
sería revertir #44, y eso devuelve la creación de cuentas al navegador, que es justo lo que se quería
cerrar. Ante un fallo del alta: mirar el log de la función en Vercel, que desde 5d80f6fe dice si es
Turnstile (`[turnstile] configuración incompleta` / `[turnstile] rechazado`) o el Admin SDK.
