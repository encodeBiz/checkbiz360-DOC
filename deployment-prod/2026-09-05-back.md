## 0. Lo primero, porque no es evidente

**El merge no arranca los servicios nuevos.** `docker-compose.yml` de producción es
**idéntico** en `main` y en `staging`: los tres servicios nuevos solo existen en
`docker-compose.staging.yml`. Y `nginx/nginx.conf` (el de producción) solo cambia en
este lote para renombrar `rentman` → `rentmanbiz`: **no tiene ni upstream ni location**
para backoffice, billing ni events.

Consecuencia: si se hace el merge y nada más, producción compila y despliega código de tres
servicios que **nunca se levantan** y a los que **no hay ruta**. No falla nada de forma
ruidosa; simplemente no existen. Los dos ficheros hay que editarlos a mano —§1 y §2 traen el
texto exacto— y hacerlo **en el mismo commit del merge**, para que el despliegue automático
los recoja de una vez.

**Y hay un cambio que sí llega solo y sí rompe:** el prefijo del add-on pasa de
`/api/v1/rentman` a `/api/v1/rentmanbiz`, sin alias, ni en nginx ni en el servicio
(`services/rentman/src/app.ts`). Todo lo que hoy llame a `/api/v1/rentman/...` en producción
—incluido el webhook que Rentman tenga registrado— empieza a dar 404 en el momento del
despliegue. Ver §8.

## 1. `docker-compose.yml` de producción — tres bloques a añadir

Añadir al final de `services:`, con el estilo del fichero de producción (sin anclas `*service`
/ `*health`, que solo existen en el de staging; `env_file` explícito en cada bloque).

```yaml
  # ── Backoffice — panel interno del equipo de soporte ──────────────────────
  # Un solo nodo: sirve la SPA (Vite, compilada dentro de la imagen) y su propia
  # API. La SPA no habla con Firestore ni con Postgres; todo pasa por esta API,
  # que es la única que conoce los roles y la que escribe la auditoría.
  backoffice:
    build:
      context: .
      dockerfile: services/backoffice/Dockerfile
    env_file: .env.production
    environment:
      - NODE_ENV=production
      - PORT=3010
    volumes: *secret-volumes
    depends_on:
      postgres:
        condition: service_healthy
    expose:
      - "3010"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3010/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped

  # ── Facturación — suscripciones de Stripe y envío de facturas ─────────────
  # No depende de Postgres: su verdad está en Firestore y en Stripe. Sin tareas
  # programadas: quien decide cuándo se cobra es Stripe.
  billing:
    build:
      context: .
      dockerfile: services/billing/Dockerfile
    env_file: .env.production
    environment:
      - NODE_ENV=production
      - PORT=3011
    volumes: *secret-volumes
    expose:
      - "3011"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3011/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped

  # ── Eventos — webhooks salientes ──────────────────────────────────────────
  # Gestiona los endpoints suscritos, sirve el catálogo y rescata las entregas
  # que no salieron a la primera. El reparto normal NO pasa por aquí.
  events:
    build:
      context: .
      dockerfile: services/events/Dockerfile
    env_file: .env.production
    environment:
      - NODE_ENV=production
      - PORT=3012
    volumes: *secret-volumes
    depends_on:
      postgres:
        condition: service_healthy
    expose:
      - "3012"
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3012/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped
```

Y en el `depends_on` del bloque `nginx`, junto a los que ya están:

```yaml
      backoffice:
        condition: service_healthy
```

Solo backoffice: es el criterio del fichero de staging, y es el correcto —nginx no debe
quedarse esperando a un servicio de facturación que puede tardar en pasar el healthcheck—.
billing y events se resuelven por nombre cuando estén arriba.

## 2. `nginx/nginx.conf` de producción — upstreams y rutas

**Upstreams**, junto a los nueve que ya hay:

```nginx
  upstream backoffice_service { server backoffice:3010; }
  upstream billing_service    { server billing:3011; }
  upstream events_service     { server events:3012; }
```

**Rutas exactas** (el bloque de `location = …` que evita el 301 hacia la barra final),
junto a la de `sales`:

```nginx
    location = /api/v1/backoffice { proxy_pass http://backoffice_service/api/v1/backoffice; }
    location = /api/v1/billing    { proxy_pass http://billing_service/api/v1/billing; }
    location = /api/v1/events     { proxy_pass http://events_service/api/v1/events; }
```

**Rutas de prefijo**, después de la de `sales`:

```nginx
    # ── Facturación. El webhook de Stripe entra por aquí: nginx pasa el cuerpo
    # tal cual, que es lo que necesita la verificación de firma.
    location /api/v1/billing/ {
      proxy_pass http://billing_service/api/v1/billing/;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
    }

    # ── Backoffice — dos entradas al MISMO contenedor: la API y la SPA
    # compilada, que ese mismo servicio sirve como estáticos.
    location /api/v1/backoffice/ {
      proxy_pass http://backoffice_service/api/v1/backoffice/;
    }

    location /backoffice/ {
      proxy_pass http://backoffice_service/backoffice/;
    }

    # ── Eventos — gestión de webhooks salientes y emisión S2S. El /s2s/ cuelga
    # del mismo prefijo pero lo protege una API key, no el token de Firebase.
    location /api/v1/events/ {
      proxy_pass http://events_service/api/v1/events/;
    }
```

Dos cosas que conviene decidir antes de pegarlo:

- **`/backoffice/` queda expuesto en el dominio público de la API.** La puerta la guarda
  `backoffice_users` (un token de Firebase válido de cualquier cliente no basta), pero es una
  pantalla interna colgando de `api.checkbiz360.com`. Si se quiere fuera del internet abierto,
  este es el momento: un `allow`/`deny` por IP en ese `location`, o servirlo por otro nombre.
  La decisión no la toma el despliegue.
- **`/api/v1/events/s2s/` va con `x-encodebiz-key`, no con token de Firebase.** Es la puerta
  por la que emiten los triggers que aún viven en Firebase. Hoy no hay ninguno montado
  (§7), así que puede quedarse cerrada al exterior sin romper nada.

Tras el `up -d`, **reiniciar nginx** — el workflow ya lo hace (`restart nginx`); si se
levanta a mano, no olvidarlo: resuelve los upstreams al arrancar y se queda con las IPs
viejas, y 8 de 9 rutas devuelven 502.

## 4. Migraciones de Postgres

Base de producción: **`encodebiz_analytics`** (la de desarrollo es `encodebiz_staging`;
**ninguna se llama `encodebiz`**).

El montaje de `./migrations` en `/docker-entrypoint-initdb.d` **solo se ejecuta si el
directorio de datos está vacío**. En producción no lo está, así que no se aplica nada solo:
**a mano y una a una, mirando el resultado de cada una.**

### 4.1 Estado de partida

`main` ya tiene `001`–`009`, `019` y `020`. Las dos últimas llegaron con el lote de sales,
así que **antes de nada hay que confirmar que están aplicadas en la base**, no solo en el
repositorio:

```sql
SELECT column_name FROM information_schema.columns
 WHERE table_name = 'sales_leads' AND column_name LIKE 'ga_%';
SELECT to_regclass('public.sales_conversions');
```

Si `ga_status` no existe o `sales_conversions` es `NULL`, aplicar `019` y `020` **antes** de

## 5. Firestore — datos que hay que sembrar

Nada de esto lo crea el despliegue. Sin ello los servicios arrancan y fallan al primer uso.

### 5.1 Plantilla de correo de la factura — `emails_template`

`EmailType.INVOICE` es nuevo. `EmailService` la busca por `type` **y** `locale`, y si no está
**lanza excepción**: el correo de la factura no sale.

Hacen falta dos documentos en la colección `emails_template`:

- `{ type: "INVOICE", locale: "es", subject: …, html: … }`
- `{ type: "INVOICE", locale: "en", subject: …, html: … }`

El idioma sale de `entity.language`; cualquier cosa que no sea `en` cae a `es`.

Nuevo en este lote: **el asunto también admite sustituciones**. Una plantilla con
`{{invoiceNumber}}` o `{{entityName}}` en el asunto ya no llega al cliente con las llaves
puestas. Copiar las dos de `dev-encodebiz`, que son las validadas.

### 5.2 Ficha del add-on — `addons/rentmanbiz`

El id del add-on es **`rentmanbiz`**, no `rentman`. El front compone
`{NEXT_BACKEND_URI_ADDONS_HANDLER}/{addonId}/{verbo}` leyendo el id del catálogo, así que este
documento es lo que hace que el prefijo nuevo de nginx (§2) y el del front coincidan.

Se siembra con el script, que hace merge y es idempotente:

```bash
docker compose exec -T rentman node services/rentman/dist/scripts/seed-addon-catalogue.js --dry-run
docker compose exec -T rentman node services/rentman/dist/scripts/seed-addon-catalogue.js
```

**Si en producción existe ya un documento `addons/rentman`** (id viejo), retirarlo o
desactivarlo después de sembrar el nuevo: si no, el panel ofrece dos fichas y una de ellas
apunta a un prefijo que ya no existe.

### 5.3 Personal del backoffice — `backoffice_users`

No hay alta automática ni primer usuario por defecto: **estar en esta colección es lo único
que abre el panel**. Un documento por persona, con el **uid de Firebase Auth como id**:

```json
{
  "uid": "<uid de Firebase Auth>",
  "email": "…@encodebiz.com",
  "name": "…",
  "role": "root",
  "active": true,
  "createdAt": "2026-09-05T00:00:00.000Z",
  "createdBy": null,
  "lastLoginAt": null
}
```

Roles: `root` (incluye gestionar el propio personal), `admin` (todo sobre los datos, nada
sobre los usuarios del backoffice) y `editor`. Crear **un solo `root`** a mano; desde el panel
se dan de alta los demás.

Desactivar se hace con `active: false`, **no borrando**: el borrado se lleva por delante la
correspondencia con el historial de auditoría.

`invoice_emails` (billing, una por factura enviada) y

## 6. Stripe

El servicio `billing` sustituye a la función `apiV100-firebaseEntryHttp-stripeWebhook`. El
plan por fases está en `DOCS/ingenieria/billing-v2/04_fases.md`, y su criterio manda sobre
este documento: **nada de cortes en seco sobre facturación**.

1. **Endpoint nuevo en el dashboard de Stripe (modo live)**, apuntando a
   `https://api.checkbiz360.com/api/v1/billing/webhook`.
2. **Eventos suscritos**, que son los que el handler trata:
   `invoice.finalized`, `invoice.paid`, `invoice.payment_failed`, `invoice.upcoming`,
   `customer.subscription.deleted`, `payment_method.attached`, `payment_method.detached`.
3. **Copiar el secreto de firma a `STRIPE_WEBHOOK`.** Stripe solo lo enseña al crear el
   endpoint; si se pierde, hay que rehacerlo.
4. **El endpoint viejo (la Cloud Function) no se borra: se deja y se decide después.**
   Mientras los dos estén activos y suscritos a los mismos eventos, cada factura se procesa
   dos veces. Lo razonable es **desactivar el viejo en el mismo gesto en que se activa el
   nuevo** —en el dashboard es un interruptor, y es el rollback más rápido que hay—.
5. **El envío de la factura desde el dashboard de Stripe debe seguir APAGADO.** Desde que la
   mandamos nosotros, ese interruptor solo consigue que el cliente reciba la factura dos veces.
6. `BILLING_SEND_INVOICE_DISABLED=true` apaga nuestro envío sin desplegar, conservando el
   registro en `invoice_emails`. Es el freno de mano si algo sale mal con el correo: sale a
   `false`.

El webhook se monta **antes** de `express.json` para conservar el cuerpo crudo, y nginx lo
pasa tal cual (§2). Si alguien mete un `proxy_set_header Content-Type` o un filtro por el
camino, la firma deja de validar y todo responde 400.

## 7. Cloud Functions — qué se despliega y qué no

**`firebase.json` es nuevo en este repositorio.** Declara el codebase `triggers` sobre
`services/firebase_sdk`. Y ese directorio **no exporta ni un trigger todavía**: es un residuo
transitorio (ADR-006 de `eventos-webhooks`) que se irá llenando y vaciando por oleadas.

> **No lanzar `firebase deploy` desde este repositorio en este pase.** Desplegar un codebase
> vacío no aporta nada y sí abre la puerta a que alguien confunda codebases y borre funciones
> que viven en `encodeBiz-SAAS`. Cuando haga falta, **siempre** con `--project` explícito:
> sin la bandera, `.firebaserc` puede llevar a producción en silencio.

### El contenedor ya emite — y eso cambia el orden

Los lanzadores de la oleada 2 entraron en `staging` **después** de la primera redacción de
este documento. Hoy `checkinbiz`, `tasks` y `documents` llaman a `emit()` en sus propios casos
de uso: **33 eventos salen de verdad** en cuanto el contenedor esté arriba y una entidad tenga
un endpoint suscrito. Ya no es fontanería en espera.

Consecuencia inmediata, y es la que hay que resolver antes del pase:

> **`onChecklogWebhook` sigue vivo en `encodeBiz-SAAS` y lee la MISMA colección de endpoints**
> (`entities/{entityId}/webhook_endpoints`). Hasta ahora no colisionaban porque el contenedor
> no emitía nada. **Ahora sí emite.** Un cliente suscrito a `attendance.clock_in` por el tipo
> exacto recibirá cada fichaje **dos veces**, con dos firmas y dos identificadores de entrega.
> El integrador lo verá como un duplicado inexplicable.

Cómo se cierra, en este orden y sin separarlo del pase:

1. Comprobar en el Firestore de **producción** si hay algún `webhook_endpoints` dado de alta.
   Si no hay ninguno, esto es teórico y se puede hacer con calma después.
2. Si los hay, **retirar `onChecklogWebhook` de `encodeBiz-SAAS` en la misma ventana** en que
   se despliega el contenedor. Antes deja de emitirse lo poco que se emite; después se abre la
   ventana del duplicado. Es el mismo criterio que ya fija
   `DOCS/ingenieria/eventos-webhooks/05_fases.md`.
3. Dejar también decidido qué se hace con `webhookWorker` (el repartidor programado del módulo
   viejo) y con sus tres endpoints HTTP de gestión.

El catálogo, en cambio, **ya no miente**: `31567c7` lo recortó a lo que realmente se emite, así
que la reserva que traía la primera versión de este documento está resuelta.

### Lo que sí sigue igual

- Las funciones de **calendario, geo, empleados y 2FA de empleado siguen desplegadas y siguen
  respondiendo**. No se retiran en este pase, y eso es deliberado: es lo que hace reversible el
  corte del front (§9) **y lo que mantiene viva la app publicada** (§9.5).
- `services/firebase_sdk` sigue **sin exportar ni un trigger**: los lanzadores viven en los
  servicios, no ahí. El aviso de no desplegar funciones desde este repositorio se mantiene tal
  cual.

## 8. Renombrado `rentman` → `rentmanbiz`

Es el único cambio del lote que llega solo a producción y que puede romper algo ya en uso.
No hay alias: el servicio monta sus routers en `/api/v1/rentmanbiz` y nginx solo proxya ese
prefijo.

Antes del merge, comprobar en producción:

1. **¿Hay alguna entidad con el add-on conectado?** Si el add-on nunca se activó en
   producción, esto es teórico y se puede pasar de largo.
2. **¿Hay un webhook registrado en Rentman apuntando a `/api/v1/rentman/…`?** Si lo hay, hay
   que reapuntarlo a `/api/v1/rentmanbiz/…` **inmediatamente después** del despliegue. Entre
   una cosa y otra, Rentman recibe 404 y reintenta.
3. **¿Hay algún cron, script o integración S2S** llamando a `/api/v1/rentman/sync/…`?

Si algo de esto vive en producción y no se puede reapuntar en el momento, la salida limpia es
añadir en nginx un alias temporal —`location /api/v1/rentman/ { proxy_pass
http://rentman_service/api/v1/rentmanbiz/; }`— y retirarlo cuando el otro extremo esté
cambiado. Es una línea, y evita el hueco.

## 9.5 Las apps móviles — lo que no se puede reapuntar

Es la parte del pase que no admite rollback por variable de entorno. **Las URLs van
compiladas en el binario**: lo que hay instalado en el teléfono de un empleado llama a donde
llama, y no hay forma de cambiarlo sin publicar en tiendas y esperar a que la gente actualice.

**La versión publicada en tiendas es `1.2.0+47`** (comprobado en consola el 2026-09-04). No
sale de `master` —que se quedó en `1.1.1+46`— sino de la línea de `develop`, entre `aae6c59`
(19-ago) y `66e9cd1` (21-ago). `develop` y `staging` van hoy por `1.3.0+48`, sin publicar.

Conviene saber cómo se llegó a eso, porque afecta a cómo se rastrea la próxima: Codemagic
construye por **tag** (`^v\d+\.\d+\.\d+\+\d+$`) y **en el repositorio no hay ni un tag**;
además el bloque `publishing` está comentado. Las subidas se hicieron a mano y git no registra
desde dónde. El número de build es la única pista, y el listado público de las tiendas no lo
enseña: hay que mirarlo en Play Console y App Store Connect. **Empezar a etiquetar cada
publicación es la forma barata de que esta averiguación no se repita.**

### Qué llama hoy la app publicada

**Al contenedor** —o sea, a lo que este pase cambia—:

| Ruta | Servicio |
|---|---|
| `POST /api/v1/checkinbiz/auth/login` | checkinbiz |
| `POST /api/v1/checkinbiz/auth/validate` | checkinbiz |
| `POST /api/v1/checkinbiz/checklogs` | checkinbiz |
| `POST /api/v1/checkinbiz/checklogs/update` | checkinbiz |
| `GET /api/v1/checkinbiz/calendar` | checkinbiz |
| `/api/v1/tasks/` y `/api/v1/tasks/:id` | tasks |
| `/api/v1/documents/` | documents |

**A Cloud Functions** —o sea, a lo que este pase NO toca—: `enable2FA`, `verify2FA`,
`addDeviceEmployee`, `users-recoverypassusers`, `generateReport` y la descarga de documentos
(`documentsHandler`).

De ahí sale la conclusión tranquilizadora y la inquietante a la vez:

- **El porte del 2FA de empleado al contenedor le es invisible a la app publicada**, porque
  sigue llamando a las funciones de Firebase. Mientras no se apaguen —y en este pase no se
  apagan (§7)—, no hay riesgo por ahí. **Apagarlas sería el corte que rompe los teléfonos.**
- **El fichaje, el calendario, las tareas y el documental sí pasan por el contenedor**, y son
  justo los módulos que más cambian. Ahí es donde hay que mirar.

### Cambios de este lote que tocan esas rutas

1. **Fichaje sin horario configurado deja de fallar.** Si no hay ni calendario de entidad ni un
   solo turno en toda la semana, antes salía error y ahora se registra con una ventana abierta
   00:00–23:59 marcada `source: "default"`. Es más permisivo, no menos: no rompe a nadie que
   fichara antes, pero **cambia quién puede fichar**. Un horario real con día libre o festivo
   sigue bloqueando igual.
2. **Geocerca unificada.** Antes había dos moldes (`address.geo` + `ratioChecklog` en la
   sucursal, `workSite.geo` + `radiusMeters` en la tarea) y dos formas de medir. Ahora hay una.
   El commit afirma comportamiento preservado y lo verificó contra los radios reales de
   desarrollo (50, 100, 201, 500 y nulo) más los bordes: 17 casos, misma respuesta. **Producción
   tiene los radios que tenga**, y el margen 0 sigue siendo una valla que solo se pasa desde el
   punto exacto.
3. **Cierre de jornada partida.** El checkout se atribuía siempre al primer turno del día.
   Corregido: cambia a qué turno se imputa un cierre, o sea el dato que ve el empleado.
4. **Calendario.** El festivo ahora dice de qué nivel viene y si se cobra; son campos añadidos.
5. **Emisión de eventos** en el fichaje. Es `void` y no se espera: no debería añadir latencia
   ni un modo de fallo nuevo al 201. Conviene confirmarlo bajo carga.

### Cómo se prueba antes del pase

Lo correcto es **cliente viejo contra servidor nuevo**: compilar la versión publicada y
apuntarla al entorno de desarrollo, que ya corre este código.

La `1.2.0+47` lo pone fácil, porque el conmutador de entorno entró justo en esa ventana
(`ea3d406`, *«el entorno manda sobre la API y falla si viene mezclado»*). **No hay que
parchear nada:**

```
flutter run \
  -t lib/main_development.dart \
  --flavor development \
  --dart-define=ENVIRONMENT=development
```

- Los tres interruptores —entrypoint, flavor y `dart-define`— tienen que decir `development`.
  El propio `main_development.dart` lo comprueba… **con un `assert`, que desaparece en
  release**. Compilar en debug, o el cerco no está.
- La primera línea de log debe decir `[entorno] development · API privada:
  http://141.95.47.135:8080`. Si ahí aparece `api.checkbiz360.com`, **parar**: eso es fichar
  sobre datos de clientes reales, y ya ocurrió una vez con una build anterior al conmutador.
- El flavor de desarrollo tiene otro `applicationId` (`com.checkbiz360.dev`): **se instala al
  lado de la app real**, no la pisa.
- Confirmar que el 8080 corre el `staging` de hoy, no uno anterior.

Para reproducirla exacta: `66e9cd1` si la app publicada tiene el diseño nuevo de asistencia,
`aae6c59` si tiene el viejo. Para contrato de API da igual — entre esas dos no cambió ni un
endpoint.

**Un dato que tranquiliza y conviene tener escrito:** desde que se publicó la `+47`, ningún
cambio de la app ha tocado modelos, repositorios ni cliente HTTP —el único commit en esa zona
es de codegen—. Ningún cambio de backend ha obligado a mover la app desde el 21 de agosto. Y
el fallo del `details` que tumbaba el fichaje no le afecta: la `+47` ni siquiera lee ese campo,
porque el `cast` lo introdujo la geocerca de tarea, que es posterior.

**Qué cubre**: las siete rutas de contenedor de la tabla de arriba, que es exactamente la
superficie que cambia.

**Qué no cubre**, y conviene no leer el verde como un permiso:

- **La pata de Firebase.** En una build de dev van a las funciones de `dev-encodebiz`, y ahí hay
  funciones retiradas que producción conserva (`documentsHandler`, por ejemplo). Verde ahí no
  dice nada de producción.
- **El camino permisivo nuevo del fichaje.** Un smoke test no lo pisa; hay que buscarlo a
  propósito, con un empleado cuyo centro no tenga ningún turno configurado.
- **Los radios de geocerca reales de los clientes.**

### Orden y compromiso

**Back primero, luego front, luego app.** La app instalada no se puede reapuntar, así que el
backend tiene que servir a la versión vieja y a la nueva **a la vez**. Y eso no es una ventana
de unos días: es hasta que la adopción en tiendas esté completa, que no la controla nadie de
aquí. Todo lo que la app publicada llama —incluidas las seis Cloud Functions de la lista— es
**contrato congelado** hasta entonces.

### La salida de emergencia: la puerta de versión mínima

La app trae —ya en la `+47`— un **cerco de versión mínima**. Lee `app_config/global` de
Firestore (`minAndroidVersion`, `minIosVersion`, números de *build*, más `androidStoreUrl` e
`iosStoreUrl`) y lo aplica en el splash: por debajo del mínimo, manda a actualizar y no deja
pasar.

Es la red por si la prueba destapa una rotura que no se pueda arreglar por backend. **No sirve
para este pase** —exige publicar la versión nueva y esperar revisión de tienda—, pero conviene
saber que existe antes de darse por atrapado.

Dos cautelas, porque es un documento de un solo campo con el que se tira a toda la plantilla:

- Comprobar **qué tiene hoy** `app_config/global` en producción antes de tocarlo.
- Un mínimo mal puesto, o una URL de tienda rota, deja a la gente **sin fichar y sin salida**.
  No es un campo que se cambie de paso mientras se hace otra cosa.

## 13. Verificación

Sanidad, desde el servidor:

```bash
cd /opt/encodebiz-api
docker compose ps
curl -fsS http://localhost/health

# Los tres nuevos, desde dentro de la red de contenedores
for s in backoffice:3010 billing:3011 events:3012; do
  echo -n "$s → "
  docker compose exec -T nginx wget -qO- "http://$s/health" || echo "SIN RESPUESTA"
  echo
done
```

Punta a punta, en este orden:

- **Backoffice** — abrir `https://api.checkbiz360.com/backoffice/`, entrar con el `root`.
  Que cargue Entidades, Empleados, Sucursales, Leads y Estadísticas. Después, en Postgres:
  `SELECT action, resource, status, created_at FROM backoffice_audit ORDER BY id DESC LIMIT 10;`
  — la sesión y cada petición deben haber quedado apuntadas.
- **Permiso de edición** — pedir permiso sobre una entidad de prueba, comprobar que llega el
  correo con el código y que sin teclearlo la edición sigue cerrada.
- **Events** — `GET /api/v1/events/catalogue` con token de Firebase; dar de alta un endpoint
  contra un bin de webhook.site suscrito a `attendance.*` y disparar
  `POST /api/v1/events/endpoints/:id/test`. Luego:
  `SELECT event_type, status, attempt, last_status, delivered_at FROM webhook_delivery ORDER BY created_at DESC LIMIT 5;`
  Debe salir `delivered` en el intento 1. **Es lo único que hoy sale de verdad** (§7).
- **Billing** — en el dashboard de Stripe, «Send test webhook» de `invoice.finalized` contra
  el endpoint nuevo: debe responder **200**. Una firma inválida debe dar **400**. Después, con
  una factura real de una entidad de prueba, comprobar que llega el correo con el PDF y que
  queda el registro en `invoice_emails`.
- **Add-on** — que el catálogo del panel enseñe **una sola** ficha de RentmanBiz y que
  `GET /api/v1/rentmanbiz/…` responda (401 sin token es buena señal; 404 significa que nginx
  no recargó).
- **Geo y calendario** — buscar una dirección desde el alta de un centro; abrir el calendario
  y la rejilla de disponibilidad.
- **Snapshot** — a la mañana siguiente:
  `SELECT snapshot_date, entities_total, checklogs_total, conversions_total FROM backoffice_snapshot_daily ORDER BY snapshot_date DESC LIMIT 5;`

Y una comprobación que no es de humo sino de regresión: **que un fichaje siga funcionando**.
Es lo que más código compartido toca en este lote.

## 14. Rollback

Por orden de rapidez, que es el orden en que sirven:

| Qué se rompe | Cómo se deshace | Cuánto tarda |
|---|---|---|
| El webhook de Stripe procesa mal | Desactivar el endpoint nuevo y reactivar el viejo, en el dashboard | segundos |
| La factura llega mal o duplicada | `BILLING_SEND_INVOICE_DISABLED=true` + reiniciar `billing` | un minuto |
| Salen webhooks duplicados a clientes | `EVENTS_RESCUE_DISABLED=true`, o desactivar el endpoint desde el panel | un minuto |
| El buscador de direcciones falla | `NEXT_BACKEND_URI_CHECKINBIZ_GEO` de vuelta a la Cloud Function | redespliegue del front |
| El calendario falla | `NEXT_BACKEND_URI_CHECKINBIZ_CALENDAR_HANDLER` de vuelta a la Cloud Function | redespliegue del front |
| El snapshot machaca Firestore | `BACKOFFICE_SNAPSHOT_CRON_DISABLED=true` | un minuto |
| `/api/v1/rentman` da 404 | alias temporal en nginx (§8) + `restart nginx` | un minuto |
| El lote entero | revertir el merge en `main` y volver a empujar | ~1 min de CI |

**Las migraciones no se revierten.** Todas son aditivas menos la `018`, que borra
`webhook_endpoint` —una tabla que solo el código nuevo conoce y que la `017` acababa de
crear—. Revertir el código no obliga a tocar la base.
